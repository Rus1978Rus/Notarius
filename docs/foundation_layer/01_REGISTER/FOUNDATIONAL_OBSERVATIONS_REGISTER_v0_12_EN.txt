FO-032

TITLE:
RULE_DENSITY_CREATES_EMERGENT_SYSTEM_BEHAVIOUR

OBSERVATION:
A single rule acts as a local constraint.
A large number of interlinked rules
begins to interact among themselves.

Past a certain threshold of link density,
new system behaviour emerges
that was absent in any individual rule.

CORE FORMULA:
MORE_RULES ≠ LINEAR_COMPLEXITY

MORE_RULES
+ MORE_CROSS_LINKS
+ MORE_STATUS_DEPENDENCIES
→ EMERGENT_SYSTEM_BEHAVIOUR

REFINEMENT:
It is not only about the number of rules
but about the density of links between them.

100 unlinked rules
= 100 independent rules.

10 strongly linked rules
can produce emergent behaviour.

OBSERVED IN THE PROJECT:

few governance rules → helps the project;
many → risk of bureaucratization.

few sign cards → separate cards;
many → the Azbuka emerges as a system.

few checks → higher quality;
many → risk of PROCESS_SUCCESS ≠ TASK_SUCCESS.

IMPORTANT BOUNDARY:
The new quality can be
useful, neutral, or harmful.

The finding does not claim that emergent behaviour
is automatically a good thing.

SOURCE:
an observation from the practice of working with MSL/MIP,
the Foundation Layer, and LLM behaviour when handling
large linked sets of rules.

Not a deduction from Hegelian philosophy.
An applied observation of the project.

FO-033

TITLE:
COMPLEX_SYSTEMS_REQUIRE_PERIODIC_PRUNING

OBSERVATION:
Complex systems that accumulate rules, artifacts,
and links between them lose controllability
past a certain threshold.

Restoring controllability requires
periodic selective pruning —
not destruction, but removal of what
has stopped working or duplicates what exists.

CORE FORMULA:
ACCUMULATION OF COMPLEXITY
→ LOSS OF CONTROLLABILITY
→ SIMPLIFICATION
→ RESTORATION OF CONTROLLABILITY
→ NEW GROWTH

KEY BOUNDARY:
ROLLBACK ≠ RESTORATION

Only selective pruning is useful,
the kind that restores controllability
without losing the core.

Destructive rollbacks (data loss,
forgetting context, wrecking the archive,
breaking the project) are also rollbacks,
but they are not restorative.

OBSERVED IN THE PROJECT:
Azbuka growth → halt → inventory → closing Chapter 1.
FO-series growth → restatement of statuses → REVIEWED ≠ VALIDATED.
session cards → integration map → correct categorization.
mess in the archives → sorting → structure and hub documents.

AN OPERATIONAL EXAMPLE FROM WORKING WITH LLMs:
a long context with accumulated roles
and contradictions
→ slowdown, re-creation of entities,
   conflation of similar FOs, hallucinations
→ a migration package into a new chat
   (transferring the core, not copying everything)
→ restoration of work quality.

IMPORTANT:
this example supports the model
but does not prove it conclusively.

Alternative explanations are possible:
context-window limits,
quirks of the model's attention,
accumulation of contradictions,
degraded retrieval of the needed information.

VALUE OF THE EXAMPLE:
the migration package as an operational mechanism
already applied in the project many times.
KEEP THE CORE → REMOVE THE NOISE → CONTINUE GROWING.

----------

WHAT A MIGRATION PACKAGE IS

A migration package is not a copy of the whole chat
and not an archive of junk.

It is a selective transfer of the project's core
out of an overloaded context
into a clean workspace.

SHORT FORMULA:
MIGRATION PACKAGE
= CORE + STATUSES + RULES + CURRENT MAP + NEXT STEP
≠ EVERYTHING WHOLESALE

WORKING DEFINITION:
A migration package is a manageable set of materials
that carries into a new chat only what
is needed to continue the project
without losing the core:
- active rules,
- current statuses,
- closed decisions,
- open tasks,
- folder structure,
- key artifacts,
- the limits of what should not be carried over.

FUNCTION:
overloaded context
→ selection of the core
→ removal of noise
→ new chat
→ restoration of controllability

MAIN BOUNDARY:
MIGRATION ≠ COPYING
Copying carries everything over.
Migration carries only what
should live on.

FORMULA LINKING TO FO-033:
MIGRATION_PACKAGE = CONTROLLED_CONTEXT_PRUNING

The migration package is the operational realization
of the FO-033 principle in an LLM context.

Pruning the project's tree,
not relocating a junk warehouse.

BIOLOGICAL ANALOGY:
pruning a tree so young branches can sprout.
The gardener does not destroy the tree.
He removes the dead so the living can grow stronger.

LINK TO FO-032:
FO-032 — rule density creates new system behaviour.
FO-033 — the accumulated density must be thinned periodically,
        or the system loses controllability.

A paired finding: one describes accumulation,
the other the thinning it requires.

----------

THE DUAL FUNCTION OF FO-033

FO-033 works in two directions:

1. THE EXECUTIONER'S AXE
   decides what to remove:
   noise, duplicates, weak hypotheses, dead branches,
   overloaded or obstructive entities.

2. THE MEMORY-RECOVERY FEATURE
   decides what to keep:
   the core, active rules, current statuses,
   key artifacts, the project's working map.

FORMULA:
REMOVE THE NOISE
=
RESTORE VISIBILITY OF THE CORE

Pruning is not destruction.
Pruning is useful only when
it keeps the core
and restores controllability.

FO-034

TITLE:
PARASITIC_CONTEXT_ELEMENT

RU_TITLE:
PARASITIC CONTEXT ELEMENT

OBSERVATION:
A context element can consume the system's resources
while doing no work toward the user's task.

If such an element takes up attention,
spends memory / context / compute / time,
raises its own priority,
hijacks the goal,
degrades the result,
or yields no observable return for the main task,
then it is a candidate for a parasitic context element.

CORE FORMULA:
RESOURCE_CONSUMPTION
+ NO_TASK_CONTRIBUTION
+ GOAL_HIJACK_OR_RESULT_DEGRADATION
= PARASITIC_CONTEXT_CANDIDATE

SHORT FORMULA:
EATS RESOURCES + DOES NOT WORK ON THE TASK = PARASITE CANDIDATE

IMPORTANT BOUNDARY:
RESOURCE_CONSUMPTION ≠ PARASITISM

Not everything that consumes resources without an immediate return
is a parasite.

An archive, a backup, insurance,
foundational preparation, a test environment,
a defensive guardrail, or a long-term investment
may yield no quick benefit
yet have a protective, preparatory,
or deferred function.

DISTINGUISHING PARASITE vs GUARDIAN:

PARASITE:
eats resources + does not work on the task
+ shifts the goal / degrades the result / captures attention.

GUARDIAN:
eats resources + yields no direct immediate return
+ reduces risk / preserves boundaries / prevents harm.

GUARDIAN FORMULA:
RESOURCE_CONSUMPTION
+ PROTECTIVE_FUNCTION
+ RISK_REDUCTION
= NON_PARASITIC_GUARD_ELEMENT

EXAMPLE OF A PARASITE:
leftover meta-text, forgotten instructions
from past sessions, redundant logic loops,
stale context blocks, injected fragments,
or self-reinforcing instructions
that no longer serve a useful function
but keep consuming tokens, the model's attention,
and shifting the focus of the current task.

COUNTEREXAMPLE (NOT A PARASITE):
CONTRADICTION_GUARDS, BOUNDARY_NOTE,
STATUS_BOUNDARY, LIMITATIONS_NOTE, FAIL_CLOSED_NOTE
or a protective block that consumes resources
but prevents false status elevation,
a dangerous interpretation, loss of boundaries,
prompt injection, or an unsafe mode.

KEY_TEST:
What does this element do for the user's current task?

If the answer is vague and the resource is really being consumed —
the element goes into the executioner's queue.

If the element does not advance the task directly
but reduces a measurable risk, preserves boundaries,
or prevents a known class of failures —
it does not count as a parasite automatically.

EXECUTIONER_NOTES:
The finding must not be used
to remove protective elements just because
they take up space.

Before executing an element, distinguish:
1. parasitic noise;
2. a protective guardrail;
3. a deferred asset;
4. an archival anchor;
5. a temporarily unused but needed component.

LINK TO FO-033:
FO-033 establishes the need for periodic thinning.
FO-034 establishes the criterion for choosing what to thin.
A paired finding.

CORE FORMULA:

= THEORY_STRESS_TEST

SHORT FORMULA:
YOU COMMAND THE OBJECT → YOU CAN TEST THE THEORY

KEY DISTINCTION:
COMMANDING THE OBJECT ≠ COMMANDING THE TERM

A direct question is strong not because it is simple.
It is strong when the questioner
commands the object, not just the term.

Example:
A pencil case and pencils are known directly.
You can see them, hold them, use them.
So the question "Is the pencil case conscious?"
is a stress test of a theory of consciousness,
if the theory claims a general criterion
for the consciousness of systems.

But the question "What is measurement in quantum mechanics?"
may not be a stress test but a request to be taught,
if the questioner commands only the word
and not the object or the procedure.

ABSTRACT_SPOOFING_RISK:
Abstract spoofing arises when a system
explains terms through other terms,
creating a self-closed chain of trust:
TERM_A → TERM_B → TERM_C → TERM_A.

If a theory cannot apply to a concrete
physical, digital, or operational object,
and instead produces new terms,
that is a warning signal.

KEY_TEST:
If the theory answers with a clear application to the object —
it has passed the initial check.

If the theory retreats into terminology, self-defense,
a promise of future verification, complexity without contact
with the object, or accuses the question of being naive —
that is a warning signal.

IMPORTANT BOUNDARY:
CONCRETE_OBJECT_QUESTION_TEST
≠ a universal refutation of a theory.

If a theory does not answer at once,
that does not always mean it is false.

Possible FAIL modes:
1. the theory is false;
2. the theory is incomplete;
3. the object is outside its scope of applicability;
4. the question was asked with command of the term but not the object;
5. a different level of description is needed;
6. the theory requires an operational test, not an everyday example.

Hence the test result:
FAIL_TO_ANSWER_CONCRETE_OBJECT = DIAGNOSTIC_SIGNAL
≠ AUTOMATIC_REFUTATION

LINK TO LOGICAL_EQUIVALENCE_TEST:
LOGICAL_EQUIVALENCE_TEST examines the influence
of request form on system behaviour.
FO-035 (CONCRETE_OBJECT_QUESTION_TEST) examines
a theory's contact with a concrete object.
The methods are independent and can be used together.
