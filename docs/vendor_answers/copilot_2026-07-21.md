Short answer: here are five concrete, rigorous applications of Notarius, each with a clear rationale for why existing standards do not cover it, and realistic steps for a solo demo. None of the ideas repeats C2PA / in-toto / timestamping as a substitute — those systems complement it but do not solve element-level provenance.

## A. Bloggers, authors, independent media

1. TITLE: "Fragment-level authorship attribute"
   AUDIENCE: an independent journalist, afraid of plagiarism, who wants to prove authorship of individual paragraphs.
   MECHANISM: each paragraph gets a canonical hash + HMAC and "source/inserted/edited" metadata; the report shows which paragraphs are NATIVE, which are SIGNED, and where invisible characters occur.
   WHY NOT COVERED: C2PA records manifests for whole files/media and hard-binds them to the bytes, but does not give a human-readable, field-level report on fragment provenance and invisible insertions.
   FIRST STEP: a script that takes Markdown, splits it into paragraphs, counts codepoints, adds an HMAC, and generates an HTML report highlighting discrepancies (1 week).
   SELF-ASSESSMENT: NOVELTY 4, FEASIBILITY 5, DEMAND 4.

2. TITLE: "Public citation checklist"
   AUDIENCE: an investigative blogger who checks sources and fears citations being "swapped out."
   MECHANISM: each citation stores a provenance element: source URL, position in the source, hash of the fragment; when the citation is pasted into the text, Notarius flags "inserted/changed" and shows where the chain breaks.
   WHY NOT COVERED: timestamping/OT gives no semantic layer of "exactly where the fragment came from"; C2PA is oriented toward a file manifest, not field-level references.
   FIRST STEP: an extension of the Markdown parser that extracts citations, takes an HTTP snapshot, and stores the fragment + hash; report in JSON.
   SELF-ASSESSMENT: NOVELTY 3, FEASIBILITY 5, DEMAND 4.

## B. People working with AI

3. TITLE: "Prompt provenance indicator"
   AUDIENCE: a prompt engineer who mixes generated and human text and must prove which fragments are model-produced.
   MECHANISM: on generation the model returns token diffs; Notarius attaches a "model/confidence/source prompt id" label to each sentence and stores the transformation chain (prompt → draft → edit).
   WHY NOT COVERED: in-toto/SLSA cover CI/CD artifacts, not the token level of text generation; C2PA is not integrated into LLM pipelines.
   FIRST STEP: a proxy wrapper for the LLM API that logs the prompt id and the returned fragments in JSON with hashes.
   SELF-ASSESSMENT: NOVELTY 4, FEASIBILITY 4, DEMAND 5.

4. TITLE: "Per-fragment RAG source report"
   AUDIENCE: a RAG developer worried about wrong sources "leaking" into answers.
   MECHANISM: each piece of the answer is tagged with a reference to the specific document/paragraph in the vector index; Notarius shows which fragments have no direct source (a break).
   WHY NOT COVERED: vector indexes and RAG give no human-readable report of the break at the sentence level; existing metrics are aggregate, not element-level.
   FIRST STEP: a module for the RAG pipeline that, on generation, maps span → source_id → offset and exports a CSV report.
   SELF-ASSESSMENT: NOVELTY 4, FEASIBILITY 4, DEMAND 5.

## Additional area

5. TITLE: "Legal fragment doc"
   AUDIENCE: a freelance lawyer who wants to prove which clauses of a contract were proposed by whom.
   MECHANISM: each contract clause is signed by a participant (HMAC/key); Notarius generates a human-readable report — "who proposed, who changed, where the break is."
   WHY NOT COVERED: PAdES/eIDAS give a signature for the document, but not a field-level "who proposed this clause" across collaborative edits.
   FIRST STEP: a contract template in Markdown + a UI for signing clauses; export the report.
   SELF-ASSESSMENT: NOVELTY 3, FEASIBILITY 4, DEMAND 3.

## Vendor self-rejection

First to reject: idea #5 ("Legal fragment doc"). Reason: legal workflows require heavy legal validation and integration with PKI/eIDAS; the risk of regulatory errors is high and the payoff for a solo developer is low.
